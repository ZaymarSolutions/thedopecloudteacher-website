Adding new columns to the IT ticketing system SharePoint list

Use this procedure when changing the IT Tickets list behind IT Ticketing System v2. A successful change lets a learner create a ticket, open an existing one, and save either record as the form evolves.

1. Create the columns

Open the IT Tickets list, choose Settings → List settings → Create column, and give each field a descriptive name. Choose Choice for a controlled set of answers, Single line of text for short entries, Multiple lines of text for notes, Person or Group for an assignee, or Date and Time for a timestamp.

2. Allow existing forms to keep saving tickets

Column settingInitial value
Require informationNo
Enforce unique values, where availableNo
IndexedOptional

Request Type, Request Category, System/Application, Business Impact, Priority, and Status all allow repeated values. Two tickets can legitimately have the same priority or affect the same application.

3. Test the list directly

Create a test ticket in SharePoint. Leave the new fields blank and save. Create a second test ticket using the same category or priority as the first. Confirm both records appear in the list.

4. Refresh the connection and add the fields

Open IT Ticketing System v2 in Power Apps Studio. Under Data, refresh IT Tickets. Select the ticket form, choose Edit fields → Add field, and add Request Type, Request Category, System/Application, and Business Impact. Repeat for any separate create or edit form. Configure defaults, visibility, and validation for each card.

5. Check the Save action

Inspect the Save button’s OnSelect. For SubmitForm(frmTicket), verify each card’s DataField maps to the intended list column and its Update returns the selected value in the expected type. For a custom Patch, review the fields written by both the create and edit paths. Substitute your actual form and control names.

6. Test and publish

In preview, create, edit, assign, and close a test ticket. Attach a file, reopen the ticket, and confirm the attachment and field values persisted. Edit a ticket created before the new columns existed. Save and publish the tested version, then repeat the checks from the published app.

7. Make fields required if needed

Once each ticket-entry path supplies the value, enable Require information on the relevant SharePoint column. Refresh the data source, check form validation, republish, and retest new and existing tickets.

Troubleshooting the edit screen

“Duplicate values were found”
Read the field name in the error. If it is a repeatable classification field, open that column in List settings, set Enforce unique values to No, and save. Refresh the app connection, publish, and retry with the same value. If the field is an intended unique ticket ID, correct the duplicate ID instead.
Assigned To shows “Find items”
This is the picker’s empty prompt. If a ticket already has an assignee in SharePoint, check the Person or Group column mapping and the picker’s default selection. A typical Items formula is Choices([@'IT Tickets'].'Assigned To'). Reopen the saved ticket to verify the selected person persists.
An active ticket shows a completion date
Compare the stored date with the date picker’s default. If completion means closure, set the date when the ticket transitions to Closed and preserve it on later edits. Decide how reopened tickets should handle their prior completion date. Hiding the card alone leaves the stored value in place.
The four new fields are missing
Refresh the list connection, select the form used on that screen, and check its field list and each card’s Visible property. Verify both the published create and edit screens.
